Findings by page

The mono tag names the Krug principle each finding fails. “Fixed” means the change is in the working tree and type-checks; nothing is committed or deployed yet.

Site-wide

layout · header · footer · Button
  • fixed
    site ID · what is this?
    The logo alone (“re.”) never told a first-time visitor what the site is.
    Header now carries the name and a one-line tagline next to the mark.
  • fixed
    search on every page
    No search outside the home hero.
    Hairline search under the nav on desktop, a full-width field at the top of the phone menu.
  • fixed
    sections vs utilities
    Favorites sat in the main nav and in the icon cluster; Home duplicated the logo.
    Nav is sections only; Delivery and Contacts replace them so the info pages are reachable without scrolling to the footer.
  • fixed
    don’t hide the obvious
    The phone number required a click to reveal; the language button cycled without showing choices.
    Direct phone and email links; a visible selector for the three languages.
  • fixed
    consistency
    Two primary-button looks: orange on the home page, an orange→amber gradient on Add to cart / Checkout.
    One primary style everywhere; the gradient variant is now an alias.
  • fixed
    accessibility
    Pinch-zoom was locked (maximumScale: 1); no skip link; no <main> landmark.
    All three added.
  • fixed
    mislabeled
    Footer said “Поддержка” above the Instagram / Facebook / Telegram icons.
    Now “Мы в соцсетях”; Telegram points at t.me/rentevent_uz.
  • open
    dead links
    Instagram and Facebook links go to instagram.com and facebook.com, not your profiles.
    Need the real URLs.
  • open
    single source
    The phone number is typed by hand in the header, footer and contacts page; the home page reads it from the API.
    Confirm +998 90 123 45 67 is the real number, or let all four read from business settings.

Home

/
  • fixed
    the home-page test
    “Всё для вашего идеального мероприятия” is a slogan; it never says what you rent or where.
    Now “Аренда оборудования для мероприятий в Ташкенте” with a concrete second line (what, from 1 day, delivery). Same in UZ and EN.
  • open
    honest controls
    The hero date picker looks like an availability filter but the products endpoint has no date parameters.
    It is remembered and carried to product pages, which is useful. Either add date filtering to the API or relabel it “Даты аренды” on the search bar.

Cart

  • fixed

    “Оформить заказ” sent guests to login, and login dropped them on the home page — the cart flow was lost.

  • fixed

    Confirmation dialog; the per-item remove button is labeled and reads “Удалить” on wider screens.

Checkout

    Shown at the top of the order summary.
  • fixed

Info pages

/about · /contacts · /faq · /delivery · /payment · /terms · /privacy
  • fixed

  • fixed

  • fixed

  • open

    Need real figures, or drop the stats.

Sets & Events

/sets · /events
  • open
    surprise
    “В корзину” on a set adds every item for tomorrow only, without asking for dates.
    Cart shows the dates, so it is recoverable, but a date prompt before adding would remove the surprise.
  • open
    wording
    Prices mix “UZS” (cards, cart, checkout) and “сум” (hero collage, terms text).
    Pick one. “сум” is what Russian-speaking customers say; “UZS” is what the code uses.

What I could not verify

Local preview shows no products. The dev server talks to api.rentevent.uz, which rejects localhost with CORS, so catalog, product, sets and events pages render their loading and empty states locally and the production site is still behind the coming-soon gate. Data-filled layouts were checked in code, and the header, hero, catalog chrome, cart and phone menu were checked in the browser. next.config.ts now has an inert /api-proxy rewrite; start the server with DEV_API_PROXY_TARGET=https://api.rentevent.uz/api NEXT_PUBLIC_API_URL=/api-proxy to see real data locally.

Next steps

  2. Send the real Instagram / Facebook URLs, the real phone number, and the About-page figures.
  3. Decide the two product calls: date filtering in the catalog, and a date prompt on “add set to cart”.
  4. Commit and push to main when happy — Railway deploys the web service on push.
